# GoalPost Glossary

| Term                         | Definition                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **GoalPost**                 | A community-first, privacy-respecting digital platform for mutual aid, collective sense-making, and relational depth. Built on a graph-based approach to relationships and meaning-making.                                                                                                                                                                                                                                                          |
| **Pulse**                    | The first-class write unit in GoalPost — a sensed shift or resonance captured within a FieldContext. All user contributions (goals, resources, stories, care points, core values) are pulse types.                                                                                                                                                                                                                                                  |
| **GoalPulse**                | A pulse representing an objective or aspiration. Has a status (ACTIVE / PAUSED / COMPLETED) and optional horizon (SHORT / MID / LONG).                                                                                                                                                                                                                                                                                                              |
| **ResourcePulse**            | A pulse representing a supportive element, tool, or piece of knowledge. Has a resourceType and optional availability score.                                                                                                                                                                                                                                                                                                                         |
| **StoryPulse**               | A pulse serving as a narrative, reflection, or catalyst. Merges legacy CarePoint and CoreValue concepts.                                                                                                                                                                                                                                                                                                                                            |
| **CarePulse**                | A pulse focused on care, wellness, or nourishment.                                                                                                                                                                                                                                                                                                                                                                                                  |
| **CoreValuePulse**           | A pulse representing a guiding principle or value.                                                                                                                                                                                                                                                                                                                                                                                                  |
| **FieldContext**             | A thematic or temporal container within a Space that groups related pulses. Can have an emergent name derived from its content. Can be NESTED (GOAL-295): a field may hold sub-contexts via `HAS_SUBCONTEXT`, up to 5 levels deep.                                                                                                                                                                                                                   |
| **Sub-context**              | A FieldContext nested under a parent FieldContext via `HAS_SUBCONTEXT` (GOAL-295). UI copy says "nested field" (renamed from "sub-field", 2026-08-24). A pure organizational overlay: the sub-context keeps its own Space `HAS_CONTEXT` edge (auth/visibility unchanged) and its pulses stay part of the whole root field's resonance scope (ADR-017).                                                                                                                                        |
| **Space**                    | A privacy boundary that owns FieldContexts. Comes in two forms: MeSpace (personal) and WeSpace (collaborative).                                                                                                                                                                                                                                                                                                                                     |
| **MeSpace**                  | A personal, private space owned by a single user. Only the owner can view and contribute.                                                                                                                                                                                                                                                                                                                                                           |
| **WeSpace**                  | A collaborative space with an owner and members. Shared access controlled by membership roles.                                                                                                                                                                                                                                                                                                                                                      |
| **SpaceMembership**          | A Person's relationship to a WeSpace, including their role (ADMIN / MEMBER / GUEST).                                                                                                                                                                                                                                                                                                                                                                |
| **Resonance**                | A semantic connection or pattern discovered (usually by AI) between two or more pulses. Represents shared themes, emotions, or meaning across contributions.                                                                                                                                                                                                                                                                                        |
| **ResonanceLink**            | A specific connection between two pulses, with a label (e.g., MOTIVATED_BY, ALIGNED_TO), confidence score, and evidence explaining the link. Created by AI, refined by humans.                                                                                                                                                                                                                                                                      |
| **FieldResonance**           | An archetypal or symbolic pattern that threads through multiple pulses (e.g., Grief, Courage, Belonging, Justice).                                                                                                                                                                                                                                                                                                                                  |
| **PromiseWeave**             | A connective container node that gives a pulse (initially a migrated care point) a navigable neighbourhood — holding the relationships between it and the people and FieldContext it implicates, so "show surrounding relationships" has a starting point to return rather than a dead end. Originates in Steve's relational "map." Modelled as a reified connector node like ResonanceLink (its own node, **not** a pulse subtype): it `WEAVES` the pulse(s) it connects and is `WOVEN_FOR` the person it concerns, surfaced within its FieldContext via a `HAS_WEAVE` context edge — directly analogous to how ResonanceLink is surfaced via `HAS_RESONANCE`. Members author weaves from the field context's "Promise weaves" section (GOAL-341); AI-proposed ones arrive `proposed` and need confirming (`kb/04-state-machines.md`). See `kb/05-data-entities.md` and `docs/promise-weave-design-spike.md` (GOAL-266).                                                                                                          |
| **Person**                   | The base node for any human in the system. Every person has the `Person` label. Additional labels (`User`, `PersonPulse`) distinguish how they relate to the platform. A bare `Person` node (no extra label) is a contact or imported record — known to the system but not yet classified.                                                                                                                                                          |
| **User**                     | A Person with the additional `User` label — `["Person", "User"]`. Has registered on the platform and can log in. Has auth credentials (password, JWT tokens), owns a MeSpace, can join WeSpaces, create pulses, and interact with the AI assistant.                                                                                                                                                                                                 |
| **PersonPulse**              | A Person with the additional `PersonPulse` label — `["Person", "PersonPulse"]`. Represents someone in a user's relational world (a mentor, friend, community elder, etc.) who does not have platform access. They share the same Person node structure (name, profile fields, embedding) but have no auth credentials and cannot log in. Created by a User within a FieldContext to capture relational knowledge about people outside the platform. |
| **Connection**               | A relationship between two Persons, with optional metadata (why, interests). Bidirectional via `CONNECTED_TO`.                                                                                                                                                                                                                                                                                                                                      |
| **Organization**             | A first-class organization / group / company / cooperative / institution named in an uploaded document (e.g. "Artisan Cooperative"). Its own node type — **not** a `Person` and **not** a pulse. Labels `["Organization", "LifeSensor", "RelationalEntity"]`. Attached to a FieldContext via `HAS_ORGANIZATION` and linked to the pulses it relates to via `MENTIONED_IN`. Created server-side only, by the doc-ingestion `create_organization` tool. Captured so members can discover and connect with it (GOAL-298). See `kb/05-data-entities.md`.                                                                                                     |
| **MENTIONED_IN**             | The edge from a `Person` or `Organization` to a `FieldPulse` when the document identifies them as *related to / named in* that pulse but **not** its author (subjects, contributors, the org offering a resource). Authorship stays on `INITIATED_BY`; `MENTIONED_IN` is the distinct "appears in / related to" edge, so a pulse can have one author and many mentioned entities (GOAL-298).                                                                                                     |
| **Document**                 | **Being retired as a node type (GOAL-354) — a document is a *type of Resource*, not a node in its own right.** The target model is a `ResourcePulse` with `resourceType: 'document'`, carrying the file as `source*` properties (the bytes stay in S3; the graph holds only the key/URL) and the ingest queue as `ingestStatus`. The schema and the migration script (`scripts/migrate-document-to-resource.ts`) have landed; the ingest/download/delete code paths have NOT yet been re-anchored, so `:Document` is still the live node until that cutover. Described below as it stands today. An uploaded source file (`.txt`, `.md`, `.pdf` in v1) anchored to a FieldContext via `HAS_DOCUMENT`. The original blob lives in blob storage (Vercel Blob); the graph node carries filename, mimeType, sizeBytes, an optional user hint, and its ingest `status` — which doubles as the ingestion work queue (GOAL-292). Source for the doc-ingestion flow — every Person/FieldPulse extracted from a Document carries an `EXTRACTED_FROM` edge back to it (provenance). Never auto-deleted; cleanup is user-driven via `deleteDocument`. See `kb/05-data-entities.md`.                                                                                                            |
| **Document Ingestion**       | The workflow that turns an uploaded Document into entities in the FieldContext. A dedicated extraction model (independent of the chat assistant) reads the Document alongside the FieldContext roster and auto-executes `create_person` / `update_person` / `create_organization` / `create_pulse` / `link_entity_to_pulse` proposals; the resulting assistant turn lands in a fresh ingest `ConversationThread`. Beyond the single pulse author (`INITIATED_BY`), extracted people and organizations named as *related to* a pulse are linked to it via `MENTIONED_IN` (GOAL-298). **Asynchronous since GOAL-292:** the upload request only queues the work (`Document.status = PENDING`, HTTP 202) and a one-minute cron worker does the extraction, so the flow is followed via `Document.status` rather than awaited. See WF-10 and ADR-018 / ADR-014 / ADR-015.                                                                                                                                                                                                  |
| **Bulk Article Import**     | The workflow that turns a spreadsheet of articles into pulses — one row becomes one pulse in a FieldContext, attributed to its author (GOAL-317). The browser parses and previews the sheet; the member confirms; the request queues the batch. **Asynchronous since GOAL-326:** `POST /api/import/articles` answers HTTP 202 with a job id and a one-minute cron worker mints the pulses, so progress is polled rather than awaited. The columns map to pulse fields directly — **since GOAL-355 including the optional `resource_type` (→ `ResourcePulse.resourceType`) and `source_url` (→ `ResourcePulse.sourceUrl`) columns**, which replaced the member workarounds of suffixing the type onto the title and parking the source link in `description`. And **since GOAL-344 each row's link is also fetched server-side and read through Document Ingestion** — the fetched article becomes a `Document` on the field (with `sourceUrl`), the extractor enriches the row's pulse and adds the people, organizations and further pulses the article names, and the receipt reports what each article yielded. A link that cannot be read (login wall, unsupported content, unreachable) leaves the row's pulse standing on the sheet's details alone. See WF-11 and ADR-019. |
| **ArticleImportJob**        | The queue node behind a Bulk Article Import (GOAL-326): `PENDING → PROCESSING → COMPLETE / FAILED`, holding the uploaded rows, the durable per-row outcomes (whose length is the resume cursor), and edges to the target FieldContext (`HAS_IMPORT_JOB`) and the member who submitted it (`REQUESTED_BY` — the authorization decision the worker acts on). Queue infrastructure, deliberately absent from the GraphQL schema. See `kb/04-state-machines.md` and `kb/05-data-entities.md`. |
| **ConversationChunk**        | A sentence-level segment of a user's conversation with the AI assistant. Gets its own vector embedding for fine-grained semantic search.                                                                                                                                                                                                                                                                                                            |
| **Embedding**                | A vector representation (1536 dimensions, OpenAI text-embedding-3-small) stored on Persons, Pulses, and ConversationChunks. Enables semantic similarity search.                                                                                                                                                                                                                                                                                     |
| **Intensity**                | A 0.0–1.0 measure of a pulse's strength or significance.                                                                                                                                                                                                                                                                                                                                                                                            |
| **Emergent Name**            | A poetic or field-given name that arises from lived experience within a FieldContext, rather than being assigned.                                                                                                                                                                                                                                                                                                                                   |
| **Assistant Mode**           | One of three AI interaction styles: Standard (direct database answers), Aiden (questions assumptions, surfaces hidden frames), or Braider (stays present with difficulty without rushing to fix).                                                                                                                                                                                                                                                   |
| **Resonance Discovery**      | A scheduled Vercel Cron Job that uses vector similarity and LLM analysis to find semantic connections between pulses across the system.                                                                                                                                                                                                                                                                                                             |
| **Person Enrichment**        | A Vercel Cron Job triggered after pulse processing that extracts themes, passions, and traits from a person's recent pulses and updates their profile.                                                                                                                                                                                                                                                                                              |
| **Human-in-the-Loop Review** | The process where users confirm, edit, or reject AI-generated ResonanceLinks before they become established connections.                                                                                                                                                                                                                                                                                                                            |
| **Log**                      | An activity record capturing mutations (pulse creation/update/deletion, space operations, member changes). Append-only.                                                                                                                                                                                                                                                                                                                             |
| **Ontology**                 | GoalPost's semantic framework (v2.3) for modeling relational dynamics, field sensing, and reciprocal care. Defines concepts like LifeSensor, RoleExpression, and ReciprocalOffering.                                                                                                                                                                                                                                                                |
| **Dashboard View**           | The card-and-button surface for navigating GoalPost content. Renders Spaces, FieldContexts, pulses, and people as discrete UI cards with action buttons (filters, tabs, mode switchers). It is the default "Dashboard" toggle in the Studio shell and the primary entry point for most users. **Not** a graph visualization — no nodes, edges, or NVL canvas.                                                                                       |
| **Graph View** *(deprecated, removed)* | A former focal-entity graph surface built on Neo4j NVL that rendered nodes as custom `EntityBubble` HTML mounted into NVL containers. **Deprecated and removed** — the Studio canvas now offers only the Dashboard View and Bloom Exploration. Bloom Exploration is the sole graph surface. Retained here only so historical references resolve. |
| **Bloom Exploration**        | The open-ended graph surface that exposes **native Neo4j NVL exploration** capabilities (free-form expansion, multi-hop browsing, query-driven views) with minimal GoalPost-specific opinionation. It is one of the two Studio canvas views (alongside Dashboard View) and the **only** graph surface since Graph View was removed. **Renders nodes natively** (only `caption` / `color` / `size` set on each Node; no HTML containers, no React-in-NVL). Built on NVL (`@neo4j-nvl/*`), never D3/Three/XYFlow. Per ADR-011, Bloom does NOT fetch — it reuses the same Apollo cache the Dashboard view already populated. |
